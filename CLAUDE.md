# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Ce fichier documente le projet en français (langue du code et des logs) pour rester cohérent avec le reste du repo.

## Vue d'ensemble

Trois sous-systèmes indépendants qui communiquent via une API REST :

1. **Scraper Python** (racine + `scrapers/`) — scrape des offres d'emploi et profils d'entreprises sur 35 sites africains de type "emploi.xx" (plateforme Drupal générique), via SeleniumBase en mode CDP (contourne Cloudflare/captcha).
2. **Backend Node.js/Express** (`backend/`) — API REST + MongoDB, reçoit les données du scraper et les sert au frontend.
3. **Frontend React** (`frontend/`) — dashboard de visualisation (Vite + Tailwind v4).
4. **Script Sénégal** (`senegal_script/`) — scraper indépendant dédié à senjob.com (site PHP, pas Drupal — distinct du pays `"senegal"` de `scrapers/countries.py` qui cible emploisenegal.com). Voir section dédiée plus bas.
5. **Script Facebook** (`facebook_script/`) — scraper indépendant des publications de groupes Facebook (`scraper.py`) et de pages Facebook analysées par l'IA OpenAI vers des JSON au format backend (`pages.py`), compte connecté manuellement ; dans l'autre sens, `share.py` prépare les publications des offres WipWork à coller dans un groupe et `post_groups.py` les publie dans une liste de groupes. Multi-pays (les 54 pays d'Afrique de `facebook_script/countries.py`, un pays actif dès que son fichier de liens existe). Voir sections dédiées plus bas.

Le scraper ne dépend jamais du frontend ; il pousse ses données au backend via HTTP (`SCRAPER_API_URL`) et/ou les persiste en local dans `downloaded_files/*.json`.

## Commandes

### Scraper (Python)
```bash
python index.py                              # tous les pays
python index.py --country burkina            # un seul pays (voir scrapers/countries.py pour les codes)
python index.py --list                       # liste les codes pays disponibles

python index.py --download-cvs                                        # CV emploi.ma, session anonyme
python index.py --download-cvs --country maroc --cv-cookie "k=v; k2=v2"  # avec cookie de session
python -m scrapers.email_extractor --country senegal --limit 20       # extraction d'emails via Google AI Mode
python setup_profil.py --profil 1            # ouvre Chrome pour connecter manuellement un profil persistant
```
Dépendances : `pip install seleniumbase beautifulsoup4 requests`. Pas de suite de tests automatisés dans ce dépôt — la validation se fait en exécutant le scraper sur un pays et en inspectant les fichiers `downloaded_files/`.

Variable d'environnement clé : `SCRAPER_API_URL` (défaut `http://localhost:3500`). La mettre à vide désactive l'envoi vers le backend et bascule sur cache JSON local uniquement.

### Envoi des CV vers l'IA WipWork (`scrapers/ia_cv_uploader.py`)
```bash
python -m scrapers.ia_cv_uploader --dry-run                  # liste ce qui partirait, aucun envoi
python -m scrapers.ia_cv_uploader --limit 5 --use-test        # test réel sur 5 CV, collections de test de l'IA
python -m scrapers.ia_cv_uploader --country south_africa
python -m scrapers.ia_cv_uploader --cv-root /srv/cv_scrappe/downloaded_files/cv_files
python -m scrapers.ia_cv_uploader --max-attempts 3            # ignore les CV ayant déjà échoué 3 fois
```
Pousse les CV déjà scrapés vers `POST {IA_API_URL}/parse/resume` (défaut `https://www.wipwork.com/bot`).

- **Sélection** : appliquée côté backend par `GET /api/cvs/ia/pending` — `commercial_email_wave = 2` (`--wave`, `all` pour ignorer), `commercial_email_unsubscribed` absent, et `ia_sent != true`. Un CV envoyé quitte donc le filtre : le script relit la page courante en boucle, aucun doublon même en cas de reprise.
- **Métadonnées** : `enterprise_ids=WipWork` + `enterprise_sources={"WipWork":"import"}` (champ **obligatoire** de l'API, `--source` pour `apply`/`save_from_search`), `country_ids` = alpha-3 déduit du pays via `scrapers/common/country_iso.py` (`south_africa` → `ZAF`), `visibility=visible`, `is_active=false` (défaut de l'API — passer `--is-active` pour activer).
- **Fichier** : lu depuis `filepath` ; si le chemin vient d'une autre machine (chemins Windows `C:\Users\user\...` en base), repli sur `<--cv-root|$CV_FILES_ROOT>/<country>/<filename>` puis `downloaded_files/cv_files/<country>/<filename>`. Seuls `.pdf`, `.docx`, `.doc` sont acceptés.
- **Marquage** : `PATCH /api/cvs/{id}/ia` écrit `ia_sent`, `ia_sent_at`, `ia_point_id`, `ia_user_id`, `ia_operation_type`, `ia_storage_path`, `ia_attempts`, `ia_last_error`, `ia_skip_reason`. Un « skip » (fichier introuvable, pays inconnu) n'incrémente pas `ia_attempts` et laisse le CV éligible ; un échec API l'incrémente. Journal local de secours : `downloaded_files/ia_uploads.json`.
- **Retry** : backoff exponentiel + jitter sur 408/429/5xx uniquement ; 400/415/422 = échec définitif (le CV est marqué `failed`, la boucle continue).

- **Authentification** : l'API IA exige un en-tête `X-API-Key`, envoyé depuis `IA_API_KEY` (ou `--api-key`). `IA_API_TOKEN` ajoute un `Authorization: Bearer` si un jour nécessaire. Les secrets ne sont jamais loggés en clair (`bf80…ddbe`).

Variables d'environnement : `SCRAPER_API_URL`, `IA_API_URL`, `IA_API_KEY`, `IA_API_TOKEN` (Bearer, optionnel), `CV_FILES_ROOT`. Le script les lit dans l'environnement, puis à défaut dans `.env` (racine) et `backend/.env` — tous deux git-ignorés, c'est là que vit la clé d'API ; ne jamais la remettre dans un fichier suivi par git. `_load_dotenv()` n'écrase jamais une variable déjà exportée dans le shell.

Vérifier la couverture du mapping pays → alpha-3 : `python -m scrapers.common.country_iso`.

### Script Sénégal — senjob.com (`senegal_script/`)
```bash
python senegal_script/scraper.py                 # interactif : login manuel puis scrape toutes les pages
python senegal_script/scraper.py --limit 5        # test rapide, 5 nouvelles offres
python senegal_script/scraper.py --max-pages 2
python senegal_script/scraper.py --headless       # sans fenêtre, suppose la session déjà connectée
```
Au premier lancement (ou si la session a expiré), une fenêtre Chrome s'ouvre sur l'espace candidat senjob.com et attend une connexion manuelle (ENTRÉE dans le terminal pour continuer) — session sauvegardée dans le profil persistant `my_custom_profile_senegal` (racine du projet). Sans connexion, les offres natives senjob (non relayées depuis un flux ONG externe) n'exposent ni email de contact recruteur ni description complète — voir "Pièges" ci-dessous.

`is_logged_in()` vérifie avant toute chose si le profil est déjà connecté (absence du champ mot de passe sur la page de connexion) — si la session est encore valide, aucune saisie n'est demandée, passage direct au scraping.

Une offre sans `company_id` identifiable (ni logo, ni nom d'entreprise) n'est jamais écrite dans `jobs_senjob.json` ni poussée à `jobs_scrappe` (destinées à une campagne d'emailing par entreprise) — trace uniquement dans `downloaded_files/jobs_senjob_skipped.json` pour éviter de la re-scraper à chaque lancement.

Fichier unique et autonome (n'importe pas `scrapers/`, dépendances dupliquées localement : `JsonStore`/`ApiClient`) — sortie dans `downloaded_files/jobs_senjob.json`, push vers `SCRAPER_API_URL` si définie (même convention que le reste du scraper).

### Script Facebook — groupes (`facebook_script/`)
```bash
python facebook_script/scraper.py                             # groupes listés dans facebook_script/pays/madagascar/groups.txt
python facebook_script/scraper.py --url https://www.facebook.com/groups/506924959474464/
python facebook_script/scraper.py --max-posts 10               # test rapide
python facebook_script/scraper.py --stop-after-known 20        # relance incrémentale (tri chrono par défaut)
python facebook_script/scraper.py --dump-html --max-posts 5    # HTML brut par publication -> downloaded_files/facebook_html/
python facebook_script/scraper.py --login                      # forcer l'étape de connexion manuelle
python facebook_script/scraper.py --no-ocr                     # sans lecture du texte des images
python facebook_script/scraper.py --max-age-days 0             # toutes les publications (défaut : 5 derniers jours)
```
Dépendances en plus du reste du dépôt : `pip install rapidocr onnxruntime` (OCR des images, optionnel).
Premier lancement : Chrome s'ouvre sur facebook.com avec le profil persistant `my_custom_profile_facebook`, connexion manuelle puis ENTRÉE dans le terminal. Session détectée par le cookie `c_user` + absence de page login/checkpoint (`_session_active`, sans navigation pour ne pas casser une 2FA en cours).

Boucle par groupe (`scrape_group`) : `COLLECT_POSTS_JS` marque les `[aria-posinset]` du `div[role="feed"]` pas encore traités (`data-scrape-key`), clique « Voir plus » et simule un survol du lien horodatage ; chaque publication est ensuite lue par `_outer_html` puis parsée en BS4 (`parse_post`). Scroll en bas de page tant que du contenu arrive ; fin du fil après `--max-idle` scrolls sans nouveauté. Sortie : `downloaded_files/facebook_posts_{group_id}.json` (clé `post_id`), écrite par lot (`PostStore`, écriture atomique). Pas de push backend (aucune route pour ces données).

Images : téléchargées avec `requests` dès qu'une publication est nouvelle (`download_post_images`), dans `downloaded_files/facebook_images/{group_id}/{post_id}_{n}.jpg` ; chemin relatif à `downloaded_files` dans `images[i]["file"]`. Les URL du CDN Facebook sont signées et expirent en quelques jours (`oe=`) : au début de chaque groupe, `download_missing_images` rattrape les publications en cache sans fichier. Erreur définitive (404, 403, 410, contenu non image) → `images[i]["download_error"]`, plus retentée ; erreur réseau → retentée au lancement suivant. `--no-images` pour ne garder que les URL. Seules les vignettes présentes dans le fil sont récupérées (taille du fil, ~600-700 px ; au-delà de 5 photos, le « +N » n'est pas dans le DOM).

Fin de chaque groupe (`finalize_posts`, hors `finally` : sauté sur Ctrl+C, rattrapé au lancement suivant car ne traite que ce qui manque) :
- **OCR** des images téléchargées sans `ocr_text` via RapidOCR (`pip install rapidocr onnxruntime`, local et gratuit, import paresseux : sans le paquet, simple avertissement). Lignes filtrées (score ≥ `OCR_MIN_SCORE`, ≥ 2 caractères alphanumériques) dans `images[i]["ocr_text"]`. Emails/téléphones trouvés sur les images fusionnés dans `emails`/`phones`. `--no-ocr` pour désactiver. Sans OCR, `_image_text` se rabat sur le texte alternatif de Facebook (« … qui dit '…' »), incomplet (a sauté un des deux emails d'une affiche réelle).
- **Offres d'emploi** : `analyze_job` recalculé pour tout le cache à chaque lancement → `post["job"]` = `{is_offer, title, description, tasks, profile}` (description = texte + texte des images). Détection par mots-clés FR/EN/malgache/portugais (+ tournures du Cameroun, 24/11/2026 : « besoin urgent des serveuses », « besoin du personnel », « nous sol(l)icitons » — jamais « besoin d'un travail / boulot / emploi », demandeur d'emploi) sur texte « plié » (`_fold` : minuscules, sans accents, NFKD), rubriques découpées sous les intitulés « Missions/Tâches… » et « Profil/Compétences… » (`_job_sections`, best-effort, fusion des lignes coupées par l'OCR).
- **Export** `downloaded_files/facebook_jobs_{group_id}.json` : uniquement les offres, champs utiles (intitulé, description, missions, profil, emails, téléphones, lien, images).

L'analyse IA, le dédoublonnage et l'envoi au backend des publications de groupes passent par `pages.py` (voir la section suivante) ; `scraper.py` seul s'arrête à l'export heuristique `facebook_jobs_<id>.json`.

Fichier autonome (n'importe pas `scrapers/`). Validation hors Facebook : fausse page de groupe locale reproduisant les pièges ci-dessous, pilotée en headless via `scrape_group` avec `OUTPUT_DIR` redirigé.

### Pages Facebook → IA OpenAI → JSON backend (`facebook_script/pages.py`)
```bash
python facebook_script/pages.py                                   # pays/madagascar/pages.txt : scraping + analyse IA + JSON
python facebook_script/pages.py --url https://www.facebook.com/profile.php?id=61559428572369 --max-posts 5
python facebook_script/pages.py --no-ai                           # scraping seul, aucun appel OpenAI
python facebook_script/pages.py --skip-scrape                     # sans navigateur : IA + consolidation du cache
python facebook_script/pages.py --skip-scrape --reanalyze         # refait les analyses d'un ancien prompt/modèle (cache utilisé)
python facebook_script/pages.py --max-ai-tokens 500000            # plafond de tokens IA pour ce lancement
python facebook_script/pages.py --no-email-filter                 # envoie aussi les images/publications sans email lu
python facebook_script/pages.py --max-age-days 30                 # fenêtre de publication (défaut 5 jours, 0 = tout)
python facebook_script/pages.py --push                            # + envoi au backend et nettoyage des doublons déjà envoyés
python facebook_script/pages.py --push-only                       # envoi des JSON déjà générés (ni navigateur ni IA)
python facebook_script/pages.py --push-only --no-clean            # envoi sans aucune suppression dans le backend
python facebook_script/pages.py --no-groups                       # pages seulement (défaut : pages.txt ET groups.txt du pays)
python facebook_script/pages.py --no-pages --push                 # groupes seulement (groups.txt du pays) : scrape, IA, base
python facebook_script/pages.py --keep-images                     # garde les images (défaut : supprimées une fois l'analyse terminée)
python facebook_script/pages.py --offer-types emploi              # annonces publiées (défaut emploi,stage : concours, formations... écartés)
python facebook_script/pages.py --allow-no-contact                # publie aussi les offres d'entreprises sans email ni téléphone
python facebook_script/pages.py --excluded-companies-file autre.txt # liste d'entreprises jamais publiées (défaut : facebook_script/excluded_companies.txt)
python facebook_script/pages.py --allow-relay-companies           # publie aussi les portails d'offres et ONG/institutions détectés par l'IA
python facebook_script/pages.py --no-suspicious-filter             # publie aussi les offres signalées comme suspectes par l'IA
python facebook_script/pages.py --keep-unverified                 # publie aussi les offres dont l'intitulé est introuvable dans la publication
python facebook_script/pages.py --skip-scrape --retranslate       # ré-analyse (prompt v8) les publications dont une offre est restée en arabe
python facebook_script/pages.py --group-url https://www.facebook.com/groups/236... --push
python facebook_script/pages.py --stop-after-known 0              # groupes : relit le fil jusqu'à la limite d'âge (défaut : arrêt après 60 connues d'affilée)
python facebook_script/pages.py --max-minutes 90                  # durée max du scroll d'une page ou d'un groupe (défaut 45, 0 = illimitée)
python facebook_script/pages.py --country cameroun                # pays/cameroun/pages.txt + groups.txt (code, nom ou ISO3 acceptés)
python facebook_script/pages.py --countries madagascar,cameroun --push
python facebook_script/pages.py --all-countries --push --headless # tous les pays qui ont un fichier de liens, à la suite
```
**Plusieurs pays** : **un dossier par pays**, `facebook_script/pays/<code>/` (`pages.txt`, `groups.txt`, `share_groups.txt` ; demandé par l'utilisateur le 24/11/2026 : le pays d'une page ou d'un groupe est celui du dossier où son lien est écrit). `countries.list_file` ; repli pour Madagascar sur les anciens `facebook_script/pages.txt` / `groups.txt` / `share_groups.txt` s'ils existent encore et que le fichier du dossier n'existe pas (déplacés dans `pays/madagascar/` le 24/11/2026). Les 54 dossiers existent avec des fichiers modèles (en-tête seul) ; `python facebook_script/countries.py --create` recrée les manquants sans jamais écraser un fichier. Un pays par lancement de `_run` (verrou `.run_<pays>.lock`, registres et sorties `*_<pays>.json` inchangés) ; `--countries` / `--all-countries` les enchaînent dans le même processus (un pays en échec n'arrête pas les suivants, code de sortie 1 à la fin). `run_daily.py` (`steps()`, relu à chaque cycle ; PM2 : `--at 19:00 --tz Indian/Antananarivo`, chaque jour à 19 h heure de Madagascar même après un redémarrage — avant : minuit si `downloaded_files/daily_schedule.json` manquait, puis dérive de la durée des cycles ; heures calculées par `run_daily.now()` dans le fuseau `--tz` (repli UTC+3 fixe sans le paquet `tzdata`), jamais via la variable `TZ` : sous Windows, Python ne comprend pas un nom IANA et se met en UTC (bug du 25/11/2026 : serveur en UTC+4, « 19:00 » attendu à 22 h à Madagascar, et `pages.py` héritait de l'heure UTC) ; lancement manqué depuis moins de 12 h (`MISSED_RUN_GRACE` : serveur ou PM2 arrêté à l'heure prévue, cycle interrompu) = rattrapé au démarrage) lance une étape `pages.py --push --headless --country <code>` par pays actif, l'une après l'autre sur le même profil. Une page ou un groupe listé pour deux pays est ignoré dans les deux (`_drop_listed_elsewhere`, comparaison sans casse) : sinon analysé deux fois (le cache IA dépend du pays) et publié sous deux pays.
`OPENAI_API_KEY` (obligatoire), `OPENAI_MODEL` (défaut `gpt-4o-mini` dans `ai_extractor.py`), `OPENAI_BASE_URL` : environnement puis `.env` / `backend/.env`. Sans `--push` / `--push-only`, **aucun envoi au backend** : fichiers JSON à valider d'abord. Même profil Chrome que les groupes (`my_custom_profile_facebook`).

Modules (importent `scraper.py` : `parse_post`, `_scroll_feed`, CDP, OCR, téléchargement) :
- `pages.py` — `PageTarget` (même interface que `GroupTarget` pour `parse_post` : `post_url()`, `source_fields()`), infos de l'onglet « À propos », fil de la page (`ScrapeOptions(any_root=True)` : publications hors `div[role="feed"]`), date complète via l'infobulle du lien horodatage (`exact_dates`, survol réel), puis **toutes** les images via la visionneuse photo (`collect_viewer_photos` : bouton « Photo suivante » jusqu'à `vignettes + "+N"` photos — la limite évite de parcourir tout un album pour une photo seule), téléchargées avec sha256 et OCR. Une publication n'est analysée que si `images_done`. Coût IA — mode mixte (`select_images_for_ai`, `images[i].ai_mode` / `ai_reason` dans `analysis_*`) : une image jointe en haute résolution coûte ~29 000 tokens avec gpt-4o-mini (mesuré : ~850 000 tokens pour 30 affiches). L'OCR lit un contact ou ≥ `AI_MIN_TEXT_CHARS` caractères → **texte OCR seul** (`ocr_text`, image non jointe) ; un peu de texte (logo) ou pas d'OCR → image jointe (`image`) ; rien lu → écartée (`skipped`), sauf si rien d'autre ne part (1re image jointe). `--send-all-images` = tout joindre. **Filtre email** (par défaut en CLI, `--no-email-filter` pour le retirer ; ignoré avec `--send-all-images`) : si le texte de la publication n'a pas d'email, une image dont l'OCR ne lit aucun email (`ocr_emails`, tolère « rh @ boa .mg ») est écartée (`ai_reason` « aucun email lu par l'OCR ») ; publication sans aucun email (texte ni images) jamais envoyée, marquée `analysis_skipped` et plus retentée tant que le filtre est actif. Mesuré sur les vraies analyses : 22 images sur 88 écartées, 37 emails sur 38 trouvés par l'IA étaient lus par l'OCR (le 38e n'était pas un email valide) ; prix : les offres sans email (16 sur 84, candidature par téléphone…) ne sont plus récupérées. Mesuré sur une vraie publication de 24 affiches : 649 662 → 11 535 tokens, mêmes entreprises et emails, plus d'offres. L'OCR part lui aussi **par lots** de `MAX_IMAGES_PER_CALL` : en un seul appel (27 000 caractères) le modèle sautait les offres des dernières affiches. L'OCR manquant est rattrapé avant l'analyse (aussi avec `--skip-scrape`). Publication déjà connue sous un autre pfbid (`KnownPosts` : au moins la moitié des photos `fbid` en commun — une photo réutilisée seule ne suffit pas — ou même texte sans photo) : ni re-scrapée ni ré-analysée (`canonical_posts`) ; ignorée à la consolidation.

**Groupes dans le même pipeline** : `pages.py` scrape aussi les groupes de `groups.txt` (`--group-url`, `--groups-file`, `--no-groups`), via `scraper.scrape_group` (cache `facebook_posts_<id>.json` et export `facebook_jobs_<id>.json` inchangés), puis `register_group` inscrit le groupe dans `pages_<pays>.json` sous l'id `group-<id>` avec `kind: "group"` et `posts_file` (relatif à `downloaded_files`) : analyse IA, dédoublonnage des entreprises/offres, JSON backend, envoi et nettoyage sont **les mêmes que pour les pages** — une offre relayée dans un groupe ET sur une page donne un seul `job_id`. `source_target()` construit la cible depuis le registre. Particularités groupes : le groupe n'est jamais l'employeur (`_without_page_owner` force `is_page_owner` à false à la consolidation, et le prompt v4 envoie le type de source + l'auteur) ; `images_done` est posé par `scraper.finalize_posts` (toutes les images ont un fichier ou une erreur définitive) ; images : après le scroll, `fetch_group_images` fait passer les publications « +N » par la même visionneuse que les pages (`fetch_post_images` sur la cible du registre : photos pleine résolution dans `facebook_pages/images/group-<id>/`, reprise si incomplet ; `--no-viewer` = 5 vignettes du fil) — les vignettes déjà lues par `finalize_posts` sont remplacées, l'OCR des nouvelles photos est rattrapé avant l'IA, et le filtre offres recalcule `analyze_job` sur les photos complètes ; **filtre offres** (`job_filter`, `--no-job-filter` pour le retirer) : une publication de groupe dont `scraper.analyze_job` ne trouve aucun mot-clé d'offre n'est jamais envoyée à l'IA (`analysis_skipped_by: "job_filter"`) — un groupe est plein de publications hors sujet. Une publication écartée par un filtre est reprise dès que ce filtre est désactivé (`analysis_skipped_by` + `_needs_analysis`) ; écartée par le filtre offres, elle est en plus réexaminée à chaque lancement avec les mots-clés à jour (`analyze_job`, regex, sans appel IA). Filtre email gardé pour tous les pays, Cameroun compris (décision de l'utilisateur, 24/11/2026, malgré 4 vraies offres sur 5 perdues dans les groupes camerounais testés : contact par téléphone / WhatsApp). Avec `--skip-scrape`, les groupes de `groups.txt` déjà scrapés par `scraper.py` sont inscrits au registre puis analysés.

**Seulement des offres d'emploi** (`offer_type`, `--offer-types`, défaut `emploi,stage`) : l'IA classe chaque annonce de `job_offers` (`OFFER_TYPES` : emploi, stage, concours, formation, bourse, appel_offres, autre ; prompt v5) et continue de toutes les lister. À la consolidation, `offer_type()` décide : règle sur le **début** de l'intitulé plié (`NON_JOB_TITLE_RES` : « Concours… », « Formation… », « Bourses… », « Appel d'offres… », « Consultation ouverte… ») prioritaire même si l'IA a dit emploi, sinon le type de l'IA, sinon (analyses d'avant v5) emploi / stage d'après l'intitulé — jamais un mot isolé : « Formateur », « Chef d'atelier », « Gestionnaire fournisseurs » sont de vrais emplois (vérifié sur les vraies offres). Une annonce écartée reçoit quand même son `job_id` (registre stable) mais n'est écrite ni dans `jobs_*` ni dans `job_publications_*` : elle va dans `analysis_<pays>.json` → `excluded_offers`, et le nettoyage du backend la **supprime sans remplaçant** (`stale_replacement_finder` renvoie `backend_push.REMOVE`) si elle y était déjà. Mesuré sur les vraies données (561 offres) : 11 écartées (7 appels d'offres, 2 formations, 1 concours, 1 bourse), aucun vrai emploi. Les entreprises ne sont pas filtrées.

**Seulement des entreprises joignables** (`require_contact`, défaut en CLI, `--allow-no-contact` pour le retirer) : une offre dont le `company_profile` n'a **ni email ni téléphone** (ou pas d'entreprise du tout) n'est pas publiée — pas de moyen de contacter le recruteur. Un seul des deux suffit (règle « email vide OU téléphone vide » écartée : 383 offres sur 561 perdues, dont 302 avec email). Même mécanique que les types : `excluded_offers[job_id].reason = "sans_contact"` (`"type"` pour concours/formation…), retirée du backend si déjà envoyée, republiée d'elle-même quand l'entreprise gagne un contact. Les entreprises ne sont pas filtrées. Mesuré (561 offres) : 72 écartées, dont 6 sans entreprise ; les entreprises qui ne recrutent que par leur site (BASAN → basan-recrute.mg, STAR) en font partie ; 8 offres avaient un email seulement dans l'offre (pas dans la fiche entreprise) et sont écartées aussi.

**Entreprises exclues** (`facebook_script/excluded_companies.txt`, une entreprise par ligne, `#` = commentaire, `--excluded-companies-file`) : ni la fiche entreprise ni ses offres ne sont publiées, et ce qui était déjà en base en est retiré (`analysis_<pays>.json` → `excluded_companies` avec la règle appliquée, offres `reason: "entreprise_exclue"` ; `stale_replacement_finder` renvoie `REMOVE` pour les deux, offres supprimées avant les entreprises). Correspondance (`excluded_company_match`) sur des **mots entiers** du nom plié, collés ou non (« EUROP'ALU » = « Europalu » = « Europ Alu », mais « YAS » ≠ « Yasmine »), pluriel simple ignoré pour les mots de 5 lettres et plus (« MINISTERES » = « Ministère de… »), sur tous les noms regroupés de l'entreprise et le nom écrit dans l'offre, ou sur le libellé du domaine de ses emails / de son site (rh@orange.mg → ORANGE ; gmail & co ignorés). Un mot courant (« orange ») écarte aussi une autre entreprise qui le porte : vérifier `excluded_companies`. Mesuré sur les vraies données : 10 entreprises et 23 offres (Npakadin 7, Yas 6, ministères 6, Europalu, AFG Bank, AXIAN, MVola), aucun faux positif (« BANKY FIRST », « Youth First » gardés) ; le ministère écrit en malgache (« Ministeran'ny … ») a sa propre ligne.

**Entreprises non-employeurs détectées par l'IA** (`company_type`, prompt v7, `--allow-relay-companies` pour retirer le filtre) : en plus d'`excluded_companies.txt` (liste nommée), l'IA classe chaque entreprise citée en `"entreprise"` (employeur direct, par défaut), `"portail_offres"` (site/page qui ne fait que relayer les offres d'autres employeurs — MADAJOB, Asako, agence de relais) ou `"ong_ou_institution"` (ONG, organisation internationale/agence de coopération — Banque Mondiale, agences UN — ou institution publique : recrutement par procédure formelle propre, pas de candidature spontanée par cette pipeline). `ai_company_type()` retient la classification la plus restrictive vue dans le cluster (une seule mention suffit). Détecté → même mécanique que la liste nommée : `excluded_companies[company_id].reason` = `"portail_offres"` / `"ong_ou_institution"` (`"liste_exclusion"` pour un nom d'`excluded_companies.txt`), fiche et offres jamais publiées, retirées du backend si déjà envoyées, republiées d'elles-mêmes si une ré-analyse change la classification. MADAJOB, Asako, PORTAL JOBS, OLONA TALENT, Banque Mondiale et World Bank sont aussi dans `excluded_companies.txt` en filet de sécurité nommé (le filtre IA n'a pas besoin de la liste pour les repérer, mais un nom connu à l'avance coûte moins cher à exclure qu'une classification IA).

**Offres suspectes** (`job_offers[].suspicious`, prompt v7, `require_contact`→`exclude_suspicious`, `--no-suspicious-filter` pour retirer le filtre) : l'IA signale les annonces avec des indices d'arnaque au recrutement (paiement/frais demandés au candidat, formation payante déguisée en préalable à l'embauche, vente pyramidale/MLM, promesses de gains irréalistes sans compétence requise, pièce d'identité ou paiement exigés avant tout entretien) — un manque de détails seul ne suffit pas. Offre marquée → `excluded_offers[job_id].reason = "offre_suspecte"`, même mécanique de nettoyage backend que les autres filtres. `_merged_offer` retient `suspicious=true` dès qu'UNE republication de la campagne est signalée, même si ce n'est pas la version la plus complète retenue par ailleurs. Les entreprises ne sont pas filtrées par ce mécanisme (seule l'offre l'est) : une entreprise par ailleurs légitime avec une offre suspecte isolée garde ses autres offres et sa fiche. (Pas de champ `suspicious_reason` : seul le booléen est retenu, pour rester sur le même modèle de filtre que les autres.)

**Secteur de l'offre** (`job_offers[].sector`, prompt v7) : l'IA déduit le secteur d'activité du POSTE lui-même (ex. "Informatique", "Comptabilité") depuis l'intitulé/les missions — distinct du `sector` de l'entreprise (`company_profile`), une entreprise pouvant recruter hors de son propre secteur (ex. un poste "Informatique" chez un employeur "Banque"). Écrit dans `detail.criteria["Secteur"]` du document `jobs_<pays>.json` (`criteria` est `Schema.Types.Mixed` côté backend, une nouvelle clé n'est donc pas supprimée silencieusement comme le serait un champ hors modèle au niveau racine).

**Vérification des réponses de l'IA** (`facebook_script/ai_checks.py`, demandée par l'utilisateur le 24/11/2026 : « pour ne pas dire n'importe quoi ») : à chaque consolidation, sans appel IA, sur une **copie** de la réponse (`check_result` ; l'analyse en cache n'est jamais modifiée, la réponse brute reste dans `analysis_<pays>.json` → `posts[].ai_result`, ce qui a été retiré dans `posts[].ai_checks`). Source = texte + OCR de chaque image + liens + champs texte de la page (`post_source`). Emails gardés s'ils sont dans la source (espaces de l'OCR tolérés) ou si leur partie avant « @ » y est (correction « gmail.corn » permise par le prompt) ; téléphones si leurs 8 derniers chiffres y sont (chiffres stylisés via NFKC) ; site si son domaine y est ; salaire si ses montants y sont ; date limite si son jour y est — sinon **retirés** (entreprises comme offres : un email inventé ne fusionne plus deux entreprises). Offre dont l'intitulé d'origine (`title_original`, sinon `title`) n'a pas au moins la moitié de ses mots significatifs dans la source (préfixe de 5 lettres : « commerciaux » = « commercial ») → `excluded_offers[].reason = "non_verifiee"` (`--keep-unverified` pour la publier quand même, `quality.verified = false`) ; intitulé encore en écriture non latine (arabe, hébreu, éthiopien, tifinagh : `FOREIGN_SCRIPT_RE`) → `"non_traduite"`, et `--retranslate` ré-analyse seulement ces publications (`_needs_retranslation` : analyse d'avant la version actuelle du prompt) ; description / éléments de liste non latins remplacés ou retirés. Exception : publication avec au moins une image **jointe** à l'IA (`ai_mode: "image"`) — l'IA a pu lire sur l'image ce que l'OCR n'a pas lu : rien retiré, signalé « non vérifiable » ; analyse d'avant v8 d'une annonce en écriture non latine : intitulé non vérifiable (traduit, original inconnu). Une campagne (republications) est vérifiée si UNE de ses occurrences l'est, et `_merged_offer` choisit la version la plus complète parmi les vérifiées. Résumé imprimé à chaque consolidation (« Vérification IA : retirés… », offres écartées par raison, origines des descriptions). Validé le 24/11/2026 sur de fausses publications seulement (pas de données réelles sur ce poste) : taux de faux « non_verifiee » sur les vraies données à surveiller dans ce résumé.

**Intitulés et descriptions générés** (`ai_checks`, 24/11/2026) : offre dont l'intitulé n'est pas un poste (`GENERIC_TITLE_RE` : « Offre d'emploi », « Recrutement », « X recrute »… — vu : affiche PROMETAL qui annonçait seulement une adresse de candidature) → `intitule_generique`, jamais publiée (l'entreprise et ses contacts restent) ; dans une description `description_generated`, toute phrase sur le candidat ou les conditions (`REQUIREMENT_RE` : expérience, diplôme, profil, salaire, contrat…) est retirée (vu : « Les candidats doivent avoir une expérience pertinente dans le domaine. » malgré le prompt). Prompt v8 resserré sur ces deux points (pas de nouvelle version : v8 n'avait tourné que sur ce poste).

**Langue et description des offres** (prompt v8, `PROMPT_VERSION = "fb-pages-v8"`) : l'IA écrit les offres en français et **traduit** fidèlement une annonce en arabe, malgache, portugais… (une annonce en anglais reste en anglais ; noms, lieux, contacts jamais traduits) ; `source_language` (ISO 639-1) et `title_original` (intitulé tel qu'écrit, sert à la vérification) ajoutés au schéma. `description` : 2 à 4 phrases d'après la publication ; publication qui ne décrit pas le poste → 1 à 2 phrases générales sur le métier, sans aucun détail propre à l'offre, `description_generated = true`. Les analyses d'avant v8 ne sont pas refaites (aucun coût) sauf `--reanalyze` / `--retranslate`. Description du document (`ai_checks.offer_description`, `quality.description_source`) : `publication` (IA), `ia_generee`, `publication_brute` (texte de la publication, seulement si elle ne contient qu'UNE offre, ≥ 80 caractères, sans écriture non latine — avant : texte de la publication même pour une publication de 10 offres), sinon `assemblee` (intitulé, entreprise, lieu, contrat, missions, profil, candidature mis bout à bout, rien d'inventé).

**Images supprimées après analyse** (`release_images`, appelé après l'analyse IA, `--keep-images` pour les garder) : les fichiers d'une publication terminée — analysée, écartée par un filtre (`analysis_skipped`), doublon de pfbid ou trop ancienne — sont supprimés du disque (mesuré : 865 fichiers, 122 Mo pour 9 pages). Tout ce qui en a été tiré reste dans le JSON (`url`, `fbid`, `sha256`, `ocr_text`, `file`) + `file_deleted: true`. Rien n'est retéléchargé : pages → `images_done` reste vrai, groupes → `download_missing_images` se fie au champ `file`. `scraper.image_on_disk()` exclut ces images de l'OCR (sinon l'analyse attendrait un OCR impossible). Une publication en attente (téléchargement, OCR, analyse, erreur IA à retenter) garde ses images. Prix : `--reanalyze`, ou `--no-email-filter` sur une publication écartée, repart du texte OCR sans pouvoir joindre les images ; le dossier d'une page vide est retiré. Fichier ouvert ailleurs (Windows) : avertissement, réessayé au lancement suivant.

Fenêtre de fraîcheur (`--max-age-days`, défaut **5** pour les pages ET les groupes — `scraper.DEFAULT_MAX_AGE_DAYS`, 15 jusqu'au 24/11/2026, réduit à la demande de l'utilisateur —, 0 = désactivé) : seules les publications des N derniers jours, aujourd'hui compris, sont récupérées — le 24 novembre, du 20 au 24 ; le 19 est trop ancien (`fb_dates.is_too_old`, date = infobulle sinon texte affiché ; date illisible = gardée). Dans `_scroll_feed` (`ScrapeOptions.max_age_days`) : publication trop ancienne ni enregistrée ni téléchargée ; `OLD_STREAK_STOP` (5) trop anciennes d'affilée arrêtent le fil (une vieille publication épinglée en tête ne l'arrête pas). Une publication déjà connue est jugée sur sa date enregistrée. Pages : les publications en cache trop anciennes ne passent plus ni par la visionneuse, ni par l'OCR, ni par l'IA ; celles déjà analysées restent dans la consolidation (déjà en base, sinon signalées à tort comme à supprimer).

**Arrêt du scroll des groupes** (`GROUP_STOP_AFTER_KNOWN` = 60, `--stop-after-known`, `--max-minutes`) : Facebook ne retire jamais du DOM les publications déjà vues d'un groupe, la page grossit à chaque scroll (mesuré : 270 000 éléments, 4,5 Go, une publication par minute après 450 publications) et finit par figer. Un groupe très actif (~80 publications/jour) faisait relire ~1 000 publications connues pour atteindre la limite des 15 jours : en tri chronologique, un groupe s'arrête donc après 60 publications déjà en cache d'affilée (le reste a été lu par un lancement précédent ; prix : une publication manquée par un ancien lancement, plus bas dans le fil, n'est plus rattrapée). Pages : pas d'arrêt sur les connues par défaut. Garde-fou commun : `--max-minutes` (45) par fil, vérifié avant chaque publication (`_time_is_up`) — sinon `run_daily.py` restait bloqué sur l'étape Facebook.

Garde-fous production (pages) :
- **Coût IA** : jamais d'appel pour une publication déjà analysée ou doublon ; `--reanalyze` ne refait que les analyses d'un autre modèle / `PROMPT_VERSION` (cache utilisé) ; erreur IA définitive non retentée sauf `--reanalyze` ; publication dont l'OCR manque = pas d'envoi (sinon chaque image partirait en haute résolution) sauf `--send-all-images` ; `--max-ai-tokens N` arrête l'analyse au budget. Cache par lot (`ai_cache/batches/`) : un lot en échec ne fait pas refacturer les lots déjà reçus. Réponse coupée (`finish_reason: length`) ou JSON illisible → lot scindé en deux (`_OutputTruncated`) ; 429 → `Retry-After` respecté ; image corrompue ou absente → pas de plantage.
- **Offres** : clé de registre par contenu (`post_id|entreprise|intitulé|date limite`), pas par rang — une ré-analyse qui renvoie les offres dans un autre ordre garde les mêmes `job_id` ; attribution en deux passes (ids connus puis ids neufs, jamais en double) ; deux offres identiques d'une MÊME publication ne sont jamais regroupées, et leur clé de registre reçoit `#2`, `#3` dans l'ordre des offres (sans ce suffixe elles partageaient une entrée et échangeaient leur `job_id` à chaque consolidation — vu sur de vraies données : offre répétée par l'IA « (H/F) » / « H/F ») ; offre sans intitulé écartée ; `merge_results` distingue les homonymes par entreprise / date limite / lieu.
- **Entreprises** : contact vu avec ≥ 2 noms dissemblables = pas une preuve pour fusionner ; vu avec ≥ `GENERIC_MIN_COMPANIES` (3) entreprises = agence / page relais, retiré aussi des fiches (`registry.generic_keys`). `names_similar` tolère les variantes de l'IA (préfixe commun ≥ 5 lettres, noms collés). Pays normalisé sur `CountryProfile.name` (filtre exact du frontend). Alias de fusion résolus en chaîne.
- **Visionneuse** : photo retenue seulement si son plus grand côté fait au moins `VIEWER_MIN_SIDE` (250 px) — pendant un changement de photo la grande image arrive après l'adresse, et une miniature de la page (100x100, cdn `t1.15752-9`) était prise à la place, puis le parcours s'arrêtait (vu : 12 photos sur 31, jusqu'à ~195 affiches manquantes sur 30 publications) ; « suivante » retentée `VIEWER_NEXT_RETRIES` fois sans jamais recliquer si l'adresse a déjà changé (sinon une photo sautée) ; attendu = vignettes + « +N » (`_expected_photos`), mais retour à une photo déjà vue = album entier (`ViewerPhotos.album_complete`, mémorisé dans `album_complete` : « +N » souvent décalé d'une photo) ; publication incomplète → `images_done` faux et reprise au lancement suivant, `VIEWER_MAX_ATTEMPTS` (3) essais (`viewer_attempts`), y compris les publications déjà terminées ; une publication déjà lue n'est jamais remplacée par moins de photos, et si la reprise en trouve plus son analyse est retirée (ré-analyse, OCR en texte seul, `job_id` déjà connus inchangés) ; fichiers nommés `<post_id>_<fbid>` (un fichier d'un essai précédent n'est jamais repris pour une autre photo). Page de connexion détectée → phase images interrompue sans marquer `images_done` ni compter l'essai ; vignettes du fil enregistrées sous `<post_id>_feed_<n>` (jamais réutilisées à la place d'une photo pleine résolution) ; avertissement après 3 échecs d'affilée.
- **Verrou** `.run_<pays>.lock` (msvcrt / fcntl, libéré même en cas de plantage) : deux lancements simultanés du même pays refusés. Au démarrage, `scraper.close_orphan_chromes` ferme le Chrome d'un lancement interrompu brutalement resté ouvert sur `my_custom_profile_facebook` (sinon profil verrouillé : `SessionNotCreatedException ... chrome not reachable`) — seulement si son lanceur (python / uc_driver) n'existe plus, jamais le Chrome d'un script encore actif.
- `ai_extractor.py` — Chat Completions + Structured Outputs (`RESULT_SCHEMA` strict) : texte, contexte de page, OCR et images (base64, ≤ 1600 px, `detail: high`) par lots de `MAX_IMAGES_PER_CALL`, fusionnés par `merge_results`. Publications sans image envoyées aussi. Cache `ai_cache/<sha256>.json` (modèle + `PROMPT_VERSION` + contenu) : changer le prompt → incrémenter `PROMPT_VERSION`.
- `ai_checks.py` — vérification des réponses de l'IA contre la publication et choix de la description (voir « Vérification des réponses de l'IA »).
- `company_registry.py` — dédoublonnage multi-pages : clés email / domaine web (hors messageries et réseaux, `GENERIC_HOSTS`) / page Facebook / téléphone E.164 / nom normalisé (sans formes juridiques) + ville ; union-find ; jamais de fusion si sites ou pages Facebook différents ; contact associé à des noms dissemblables = « partagé » (page relais, agence) et ignoré. `company_id` = `fb-<sha1>` stable via `identity_registry_<pays>.json` (fusion de deux ids connus → alias).
- `countries.py` — les 54 pays d'Afrique : `CountryProfile` (nom français = champ `country` du backend, ISO3, indicatif, longueurs du numéro national `national_number_length` + `other_lengths`, `trunk_prefix` vide là où il n'y a pas de 0 national — Cameroun, Sénégal… ; au Bénin, en Côte d'Ivoire et au Congo le 0 initial fait partie du numéro —, `lang` fr/en/pt, `display_name` / `in_phrase` des publications, `api_name` WipWork) ; codes = ceux de `scrapers/common/country_iso.py` quand le pays y est ; `find_country` accepte code, nom, ISO3 et variantes ; `python facebook_script/countries.py` liste les pays et leurs fichiers actifs. Longueurs de numéro des nouveaux pays tirées des plans de numérotation publiés, pas encore vérifiées sur de vraies données ; `fb_dates.py` — infobulle ou « 3 j » → `published_at` + précision.

Sorties `downloaded_files/facebook_pages/` : `companies_<pays>.json` (champs **exactement** ceux de `company.model.ts`), `jobs_<pays>.json` (`job.model.ts` : missions dans `detail.sections[{heading:"Missions",…}]`, lieu/secteur/contrat/salaire/date limite/source dans `detail.criteria`, `company_profile` = document entreprise), `job_publications_<pays>.json` (`job_publication.model.ts` : `{job_id, published_at}`), `analysis_<pays>.json` (revue : réponses IA, sources, fusions, et ce que le backend ne stocke pas — adresse, produits/services, catégories). Téléphones au format local (`0341234567`) dans les documents, E.164 pour le dédoublonnage.

Offres republiées (`dedupe_offers`, pages relais qui republient la même offre plusieurs jours) : même entreprise (`company_id`, sinon nom normalisé), même intitulé normalisé (`_title_key` : sans accents, sans « (e) » / « H/F »), même date limite (`_deadline_key`), publications à ≤ `JOB_REPOST_WINDOW_DAYS` jours d'écart → **un seul job_id**, `published_at` = 1re publication, contenu = version la plus complète (`_merged_offer`) avec les contacts de toutes les republications. Offre sans intitulé ni entreprise : jamais regroupée. Une offre sans nom d'entreprise est rattachée à l'unique entreprise de sa publication (`_offer_company_id`). `job_id` stable : `job_registry_<pays>.json` retient le job_id de chaque publication d'offre (ne pas le reconstruire depuis la date de 1re publication : elle change quand une publication plus ancienne est découverte). Détail des regroupements : `analysis_<pays>.json` → `jobs[job_id].occurrences`.

Envoi au backend (`backend_push.py`), **uniquement** avec `--push` (après consolidation) ou `--push-only` (JSON déjà générés, ni navigateur ni IA) : `GET /health`, puis `POST /api/companies` → `POST /api/jobs` → `POST /api/jobs/:job_id/publication` (entreprises d'abord). Incrémental : `push_state_<pays>.json` = sha256 de chaque document envoyé avec succès, un document inchangé n'est pas renvoyé (`--force-push` pour tout renvoyer) ; 4xx = refusé et non marqué, réseau/5xx = retenté. `SCRAPER_API_URL` (défaut `http://localhost:3500`, vide = désactivé).

Nettoyage des doublons déjà envoyés (`backend_push.clean_stale`, après l'envoi, désactivable avec `--no-clean`) : un id présent dans `push_state` mais plus dans les JSON (entreprise fusionnée, offre republiée regroupée, offre d'un doublon de pfbid) est supprimé par `DELETE /api/jobs/:job_id` (supprime aussi sa date de publication) puis `DELETE /api/companies/:company_id`, **seulement** si `pages.stale_replacement_finder` lui trouve un remplaçant déjà envoyé avec son contenu actuel :
- offre : même intitulé comparable (`_offer_signature` : sans « (Réf …) », « (ère) », « .ve », « H/F ») et même entreprise (alias du registre d'identité résolus), ou même publication d'origine (`analysis_<pays>.json` → `duplicate_posts` ramène un doublon de pfbid à la publication gardée) ;
- entreprise : alias vers une entreprise des JSON, et plus aucune offre en base qui la référence (offres nettoyées d'abord).
Sans remplaçant (ex. offre trouvée seulement dans l'analyse d'un doublon, absente de celle de la publication gardée) : gardé en base, signalé à chaque envoi. Remplaçant refusé par le backend : suppression reportée. Document déjà supprimé à la main : retiré de `push_state`. Routes DELETE absentes (backend lancé avant leur ajout, `npm run dev` ne recharge pas) : 404 → message « redémarrez le backend », rien supprimé, réessayé au prochain envoi.

**Pool de comptes** (`facebook_script/share_accounts.json`, `account_pool.py` ; spec `docs/superpowers/specs/2026-11-24-repartition-comptes-facebook-design.md`, validée le 24/11/2026) : actif dès qu'un compte a `"active": true` (et sans `--profile`) ; sinon fonctionnement ci-dessus **identique au caractère près** (référence `test_pool_legacy_compat.py`, produite avant le pool). Tous les groupes à publier de tous les pays choisis sont répartis entre les comptes : chaque groupe à **un seul** compte **membre confirmé**, quota **global par compte** (`max_groups_per_day` du compte > `defaults` ; `--max-groups-per-day` l'impose à chaque compte ; **0 = illimité** ; pour arrêter un compte : `"active": false`), charge équilibrée tous pays confondus — un compte peut publier dans plusieurs pays le même jour. Algorithme (`allocate`) : groupes par priorité (jamais publié, puis `last_post_at` le plus ancien, puis pays qui attend depuis le plus longtemps, Madagascar, code, rang) servis au membre libre le moins chargé, avec échanges entre membres quand tous sont au quota (ensemble servi maximal, le plus prioritaire), puis équilibrage par chemins (charge max minimale, vérifié contre une recherche exhaustive : `test_pool_optimality.py`). Rotation : un groupe non servi garde son ancienneté et passe devant au cycle suivant (rien de plus à stocker). Adhésion : `member` / `not_member` / `unknown`, preuve la plus récente entre l'historique des publications (`posted`, `pending`, `unknown`, `suspended`, `pending_limit` = membre ; `not_member`) et `--check-membership` ; une adhésion inconnue n'est jamais supposée ; le compte historique est membre de tous les groupes où il a déjà publié. Restrictions : `suspended` et `pending_limit` (modération du groupe envers nos publications) bloquent le groupe pour **tous** les comptes jusqu'à leur fin ; non-membre, limite anti-spam, déconnexion, quota, profil occupé n'arrêtent que le compte. Compte arrêté en cours de cycle (`AccountLimited` → pause de 24 h, déconnexion, profil occupé) : ses groupes restants, dans tous les pays, **ne sont jamais transférés** pendant le cycle ; les autres comptes continuent. Exécution : comptes dans l'ordre du fichier, **un seul Chrome par compte** pour tous ses pays (`publish_account` → `run()` pays après pays) ; `profile_session` tient le verrou `downloaded_files/facebook_share/.profile_<nom>.lock` de l'ouverture à la fermeture de Chrome (aussi pour `publish_country`, `--login`, `--check-membership`) : un profil déjà ouvert est sauté, jamais attendu. Même compte Facebook (cookie `c_user`) dans deux dossiers de profil → second profil refusé (`share_account_ids.json`). `--check-membership [--account P] [--recheck] [--max-groups N]` : lecture seule (aucun clic : « Exprimez-vous… » vu = membre, « Rejoindre » sans lui = non membre, bandeau = membre + restriction), groupes `unknown` ou `not_member` depuis plus de 7 jours, pause 20-40 s, écrit seulement `share_membership.json` après chaque groupe (verrou court, entrées du compte seulement) ; indépendante de la publication (peut tourner pendant que PM2 publie avec un autre profil). `--membership-summary` : tableau des adhésions sans Chrome. `--join-assist --account P` (terminal obligatoire, fenêtre visible, tous les pays par défaut, `--max-groups N`) : ouvre un par un les groupes où P n'est pas membre confirmé ; **l'utilisateur** clique « Rejoindre » et répond aux questions des admins, puis ENTRÉE (`s` = passer, `q` = arrêter) ; adhésion revérifiée en lecture seule (`membership_status`) et enregistrée ; demande en attente d'approbation = pas encore membre, revérifiée par `--check-membership`. Le script ne clique jamais « Rejoindre » (demandes automatiques en masse = signal de spam ; règle de l'utilisateur du 24/11/2026). `share_accounts.json` ou `share_membership.json` illisible → arrêt avec message, jamais réécrit. **Non vérifié sur le vrai Facebook** (à faire avant d'activer le pool, plan Task 11) : qu'un non-membre d'un groupe public ne voie pas « Exprimez-vous… ». Mise en service et retour arrière : `docs/superpowers/plans/2026-11-24-repartition-comptes-facebook.md` (tous les comptes à `"active": false` = ancien fonctionnement au cycle suivant).

**Quota** (`max_groups_per_day`, `--max-groups-per-day`, défaut 0 = aucun) : publications au plus par jour et par profil, **tous pays du profil confondus** (`posts_today` relit les suivis de tous les pays : statuts `posted` / `pending` / `unknown` / `publishing` du jour, profil de l'entrée `history[].profile`, sinon profil actuel du pays) ; avec un quota, les groupes jamais publiés passent d'abord puis ceux dont `last_post_at` est le plus ancien (rotation : chaque groupe servi tous les quelques jours). Sans quota, ordre du fichier (inchangé). `--max-groups` = par pays et par lancement.

**Anti-doublons** (en plus de `offer_key` par groupe) : même groupe sous deux adresses (nom personnalisé et id numérique) → id numérique lu à l'ouverture (`GROUP_ID_JS` : balise `al:android:url` / `al:ios:url` `fb://group/<id>`, sinon valeur `"groupID"` la plus fréquente de la page ; aucun id trouvé = rien bloqué ; **non vérifié sur le vrai Facebook**, seulement sur une fausse page locale), enregistré dans `numeric_id` / `numeric_id_source` du suivi ; la deuxième adresse → `duplicate_group` (pas ouverte), puis écartée dès la préparation aux lancements suivants (`group_identity`, `build_claims`). Même groupe dans les listes de **deux pays** → ignoré dans les deux, `[ERREUR]` à chaque lancement.     └── base_scraper.py           # BaseJobScraper(config, api_url) — orchestration Selenium principale

`scrapers/emploi_scraper.py` définit `JsonStore` (cache JSON par `job_id`/`company_id`) et `ApiClient` (POST vers le backend) ; `base_scraper.py` les importe (`from scrapers.emploi_scraper import ApiClient, JsonStore`). Ce fichier contient aussi une classe `EmploiMaScraper` historique câblée en dur sur emploi.cg — code legacy, ne pas l'utiliser comme référence pour du nouveau pays ; passer par `CountryConfig` + `BaseJobScraper`.

### Flux principal (`BaseJobScraper.scrape_all`)
1. `_scrape_recruiter_list` : parcourt les pages de `recruiters_url`, collecte les entreprises (id + nom).
2. Pour chaque entreprise : `_get_or_scrape_company` (cache-first) puis, si `has_jobs`, `_scrape_company_jobs` qui pagine les offres et scrape chaque détail via `_scrape_job_detail`.
3. Chaque offre/entreprise nouvellement scrapée est écrite dans le `JsonStore` local **et** poussée au backend si `api_client` est configuré.
4. `CloudflareBlockError` déclenche une pause de 5 min puis relance toute la session Selenium (pas juste la page).

### Patterns importants
- **Cache** : `JsonStore` — clé = `job_id` ou `company_id` ; `job_already_scraped` interroge le backend en priorité (`api_client.job_exists`), sinon le cache local.
- **Skip** : offre déjà connue → ignorée ; entreprise sans offres (`has_jobs=False`, détecté via présence d'un lien `is_recruiter_nid`) → pas de scraping de ses jobs.
- **Retry** : 3 tentatives sur pages détail/entreprise, 5 sur pages listing, `refresh()` + `maybe_solve_captcha` entre chaque tentative.
- **CDP mode** : `sb.activate_cdp_mode()` requis dès l'ouverture — ne jamais lire `sb.driver.page_source`, toujours `sb.get_page_source()`.
- **Pagination** : `?page=N`, `get_total_pages()` cherche `li.pager-item a[title='...']` (titre FR/EN selon le pays).
- **Sortie fichiers** : `downloaded_files/jobs_{code}.json`, `companies_{code}.json`, `cv_files/{code}/`, `company_emails.json`.
- **Profils Chrome persistants** : `my_custom_profile*` (créés/connectés via `setup_profil.py`), utilisés pour garder des sessions authentifiées entre lancements (ex. Google AI Mode pour `email_extractor.py`).

### CountryConfig — champs clés
```python
CountryConfig(

    base_url="https://www.emploiburkina.com",
    jobs_search_path="/recherche-jobs-burkina-faso",
    recruiters_path="/employer",          # "/recruteurs" (FR) ou "/recruiters" (EN)
    recruiter_path_prefix="/recruiter/",  # "/recruteur/" (FR) ou "/recruiter/" (EN)
    cv_storage_path="/sites/default/files/private/cv/",  # optionnel, pour cv_downloader
```

Ajouter un pays = ajouter une entrée dans `scrapers/countries.py` ; tout le reste (URLs, extraction d'ID, pagination) suit automatiquement via les propriétés/méthodes de `CountryConfig`.

## Backend (`backend/src/`)

- `app.ts` — Express, CORS, middleware de log de chaque requête, monte `/api/jobs`, `/api/companies`, `/api/cvs`, `/health`. Port via `process.env.PORT` (défaut 3500).
- `models/` — Mongoose : `job.model.ts`, `company.model.ts`, `job_publication.model.ts` (historique de publication d'une offre), `cv.model.ts`.
- `job.model.ts` : `country` (indexé ; `GET /api/jobs?country=` cherche `country` OU `company_profile.country`, les anciennes offres n'ont que le second), `language` (langue du texte enregistré), `source_language` (langue d'origine avant traduction), `quality` (`verified`, `translated`, `description_generated`, `description_source`, `checks` : remarques de `ai_checks`) — écrits par le script Facebook, absents des autres sources ; `company_id` indexé.
- `validation/payloads.ts` — `validateJob` / `validateCompany`, appelés par `POST /api/jobs` et `POST /api/companies` AVANT l'écriture : `job_id` / `company_id` et `title` (offre) non vides, types des champs connus (textes, listes de textes, objets, booléens de `quality`) ; 400 avec `errors` (liste) sinon — les scrapers affichent l'erreur et le document n'est pas marqué envoyé. Champs inconnus non vérifiés (Mongoose les supprime). Validé le 24/11/2026 : documents du script Facebook et d'`emploi.xx` acceptés, offre sans intitulé / mauvais types refusés ; nouveaux champs conservés par Mongoose (`new Job(...).toObject()`, sans base).
- `routes/` — `jobs.routes.ts`, `companies.routes.ts`, `cv.routes.ts` ; c'est l'API que consomment à la fois le scraper Python (upserts) et le frontend (lecture). `DELETE /api/jobs/:job_id` (offre + sa date de publication) et `DELETE /api/companies/:company_id` servent au nettoyage des doublons du script Facebook ; ils répondent 200 avec `deleted: false` si le document n'existe plus, pour qu'un 404 signale une route absente.
- Routes dédiées à l'envoi IA (dans `cv.routes.ts`) : `GET /api/cvs/ia/pending` (sélection `commercial_email_wave` + non désinscrits + non envoyés — déclarée **avant** `GET /api/cvs/:id`, sinon Express l'intercepte), `GET /api/cvs/ia/stats` (avancement), `PATCH /api/cvs/:id/ia` (marquage `sent`/`failed`/`skipped`). Le filtre est centralisé dans `buildIaSelectionFilter()`.
- `commercial_email_wave` / `commercial_email_unsubscribed` sont écrits par l'outil d'emailing (écriture Mongo directe, hors backend) ; ils sont déclarés dans `cv.model.ts` uniquement pour documenter la sélection IA.
- `config/db.ts` — connexion MongoDB.

## Frontend (`frontend/src/`)

- **Proxy dev** : `/api` → `http://localhost:3500` (dans `vite.config.ts`) ; en prod, `API_BASE_URL` vient de `VITE_API_URL`.
- **Tailwind v4** : un seul `@import "tailwindcss"` dans `index.css`, plugin `@tailwindcss/vite` (pas de `tailwind.config.js` classique).
- Couches : `api/` (fetch bruts) → `services/` (logique métier, ex. `filterCompanies()` côté client dans `companiesService.ts`) → `hooks/` (`useCompanies`, `useJobs`, `useStats`) → `components/` (`ui/` génériques, `layout/`, `dashboard/`) → `pages/` (`Dashboard.tsx`, `CompanyDetail.tsx`).
- Pas de pagination serveur pour l'instant : le dashboard fetch avec une grosse limite (ex. 500 entreprises) et filtre/pagine côté client.
- Icônes : `lucide-react`.

## À ne pas faire

- Ne pas utiliser `sb.driver.page_source` en mode CDP → toujours `sb.get_page_source()`.
- Ne pas appeler `sb` en dehors du bloc `with SB(...) as sb:`.
- Ne pas dupliquer la logique d'URL/extraction d'ID pays — tout passe par `CountryConfig`.
- Ne pas prendre `scrapers/emploi_scraper.py::EmploiMaScraper` comme modèle pour un nouveau scraper — c'est du code legacy spécifique à un site ; le chemin courant est `BaseJobScraper` + `CountryConfig`.
- Ne pas envoyer un CV à l'IA sans `country_ids` : les téléphones stockés sont au format local (`0786004809`), pas E.164 — l'API ne peut rien déduire et répond 400. Si un pays n'est pas dans `country_iso.py`, le CV est volontairement skippé (jamais envoyé avec un pays approximatif).
- `senegal_script/scraper.py` (senjob.com) : ne jamais parser le bloc `<script type="application/ld+json">` avec `json.loads()` — le champ `description` contient des retours à la ligne bruts qui font planter le parsing JSON strict ; extraire les champs par regex ciblée (voir `_parse_json_ld`). Les emails de recruteur n'apparaissent dans le HTML que pour une session candidate connectée (jamais en anonyme) — toujours passer par le profil persistant `my_custom_profile_senegal`.
- `facebook_script/scraper.py` : ne pas lire les publications avec `innerText`/`outerHTML` côté page ni `sb.cdp.get_element_html()` — l'horodatage (« 1 h ») est dans un shadow root **fermé**, seul `DOM.getOuterHTML(includeShadowDOM)` le sérialise (`<template shadowrootmode="closed">`). Parser ce HTML avec `string_containers=SOUP_STRING_CONTAINERS` : avec les réglages par défaut, BeautifulSoup exclut le texte des `<template>` de `get_text()`. Ne pas passer par `sb.cdp.find_element()` par publication (refait un `DOM.getDocument` complet, très lent sur Facebook) — `_outer_html` passe par `Runtime.evaluate` → `objectId`.
- `facebook_script/scraper.py` : le vrai permalien n'est dans le lien horodatage qu'après survol (href factice `?__cft__...#?bek` avant) ; sans lui, `post_id` = `hash-…` dérivé du contenu. Les blocs `aria-hidden="true"` répétant « Facebook » sont des leurres anti-scraping — toujours les exclure du texte. Les `[role="article"]` imbriqués dans une publication sont des commentaires (retirés avant parsing). Une fois « Voir plus » cliqué, Facebook insère un bouton « Voir moins » dans la dernière ligne du texte : ne jamais l'ajouter à `SEE_MORE_LABELS` (le JS le cliquerait et replierait le texte) — il est dans `SEE_LESS_LABELS`, uniquement retiré du texte côté Python.
- `facebook_script/scraper.py` : depuis octobre 2026 l'heure du lien horodatage est dessinée en SVG (`<use>`) et son texte (« 6 octobre à 10:46 ») est dans un `<span id>` **hors** de la publication, référencé par `aria-labelledby` : `_outer_html` le recopie dans `data-label-text` avant la sérialisation, lu par `_parse_time_text` (sans lui, `time_text` vide). Toutes les infobulles déjà affichées restent dans la page (`[role="tooltip"]`, y compris celles du survol synthétique de `COLLECT_POSTS_JS`) : `DATE_TOOLTIP_JS` peut renvoyer celle d'une autre publication, et `fb_dates.dates_agree` écarte une infobulle qui contredit le libellé (vu : 6 publications du 13 octobre datées du 5).
- `facebook_script/scraper.py` : depuis novembre 2026 (vu le 24/11/2026, en headless comme en fenêtre), le lien horodatage est un lien ordinaire vers le permalien avec l'heure en texte visible (« 1 h », « 58 min », « 8 octobre à 16:11 »), sans `<template>` ni `aria-labelledby` : sans le 3e passage de `_find_time_anchor` (permalien `POST_ID_RES`, hors `comment_id=`), **toutes** les publications étaient sans date (et le filtre des 15 jours ne les écartait plus). Un lien n'est retenu comme horodatage que si son texte visible est vide ou lisible par `fb_dates.parse_facebook_date` (sinon « Voir la traduction » était pris pour l'heure). Pas d'infobulle de date complète vue ce jour-là : la date vient du texte affiché.
- `facebook_script/scraper.py` : ne pas régler le niveau de log de RapidOCR via `logging.getLogger("RapidOCR")` — le constructeur le réinitialise ; passer `params={"Global.log_level": "error"}`. Les regex d'emails/téléphones s'appliquent après `_contact_text` (NFKC + retrait des emojis « keycap ») : les publications écrivent souvent les numéros en chiffres stylisés (`𝟎𝟑𝟒`, `0️⃣3️⃣4️⃣`). Dans `_heading`, une ligne sans « : » qui finit par `;` `,` `.` n'est jamais un intitulé (sinon « … sens des responsabilités; » ouvrirait une rubrique « tâches »).
- `facebook_script/pages.py` : dans la visionneuse, ne lire une photo que si l'image est chargée (`complete && naturalWidth > 0`) — pendant un changement de photo `img.src` peut valoir l'URL de la page, téléchargée alors comme « image » HTML. Ne pas considérer la page qui publie comme l'entreprise des offres qu'elle relaie : seul `is_page_owner` (décidé par l'IA) lui rattache l'id de la page et son logo. Ne pas ajouter de champ hors modèle Mongoose dans `companies_*`/`jobs_*` (supprimé silencieusement à l'upsert) : les informations sans champ backend vont dans `analysis_*`.
- `facebook_script/scraper.py` : `PROFILE_DIR` (utilisé par `pages.py` et `scraper.py`) doit rester `my_custom_profile_facebook`, distinct du profil de `post_groups.py` (`my_custom_profile_facebook_share`) — deux Chrome ne peuvent pas ouvrir le même profil : le second échoue après ~2 min (`SessionNotCreatedException` « chrome not reachable »). Du 11 au 15/11/2026, `pages.py` n'a rien scrapé, analysé ni envoyé : le profil était partagé et tenu toute la journée par un `post_groups.py` figé. Toute commande Chrome passe par `_cdp_wait` (`CDP_TIMEOUT` 60 s, puis `CdpTimeout` ; `asyncio.shield` pour qu'une réponse tardive ne tombe pas sur une `Transaction` annulée de SeleniumBase) — ne jamais appeler `sb.cdp.evaluate` / `sb.cdp.page.send` sans elle. `_activate_cdp_mode` installe `_answer_js_dialogs` : les boîtes natives sont refermées, « Quitter la page ? » acceptée — sans réponse, un brouillon laissé dans la fenêtre de rédaction figeait l'onglet au `goto` suivant (`evaluate` sans retour, reproduit sur une page locale avec `beforeunload`).
